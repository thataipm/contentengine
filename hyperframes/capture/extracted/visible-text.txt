I hand-built AI video components all session in a Remotion pipeline: a terminal card, a
counting number that rolls up to its target, a container that visibly holds items, a circular
loop diagram, a parent-to-child "spawn" device for showing an AI subagent being delegated work.
Each one was coded from scratch, one at a time, because nothing already fit what the shot
needed.

Then I checked HyperFrames, an open-source video-from-HTML framework built by HeyGen
(heygen-com/hyperframes on GitHub, Apache 2.0 license, 40,680 stars, 3,873 forks, created
2026-03-10, actively maintained). Its component registry has 380 real items: 150 blocks and 221
components, plus 9 examples.

Specific, checkable overlaps with what I'd just spent a session hand-building: 14 different
styled terminal/CLI card variants (the `code-snippet-apple-terminal-*` family), a component
literally named `count-up` that does exactly what my hand-built CountUp component does, and a
component called `scan-band` (with a sibling `light-sweep-pass`) that is the same scanning
light-sweep technique I invented by hand this session for a screenshot component, thinking I was
solving a novel problem.

One real gap survived the check: no ring, loop, or cycle diagram primitive exists anywhere in
the 380 items. I confirmed this by reading the full registry name list, not by assuming. My own
hand-built CycleWheel component, built for a product-lifecycle explainer shot, would still need
to be hand-built even on HyperFrames. The best library still has real gaps, worth checking
before assuming either way.

The takeaway: before hand-building a video/motion-graphics component from scratch, check
whether a registry already has it. This channel is switching its production to HyperFrames
starting with this exact video, and the process of switching tools is itself being shown in
public, matching this channel's positioning: building real AI automation systems, in public,
not researched and narrated from a distance.
